Neon3 / Declarative UI / V1

把界面写成声明，把事实留在领域。

NUI Flow 是 Neon3 的紧凑、逐行、可验证 UI 描述格式。它描述层级、布局、类型化输入和语义意图；解析、编译、像素、命中测试与业务真相分别由正确的 owner 负责。

01 / Start Here

先写出一份能解释自己的 Flow

最短的学习路径不是背完整 grammar，而是先建立三个判断：节点是什么、数据从哪里进来、交互要向哪个领域发出什么意图。

搜索 15 个章节
节点是静态拓扑

每一行声明一个稳定 semantic key。运行时可以隐藏预编译分支或实例化有界模板，但不能让 Flow 代码无限创建节点。

输入是类型化握手

领域服务把已准备好的 bool、数字、文本句柄、网格窗口等值发布到 input slot。Flow 只声明绑定，不推断业务事实。

事件是语义请求

event terrain.tool.select 描述意图，不声明 handler。路由、权限、事务和项目写入留在应用/领域 owner。

最小文档

version 1
surface hello column w 420 h 220 gap 12 pad 16 align stretch fill #11191F
  text title h 28 value "Hello, NUI Flow"
  text body value "One surface. Stable keys. Typed inputs."
  button save h 36 value "Save" event app.save

逐行读法

version 1使用 Flow V1 语法。新版本必须显式升级，旧 parser 不会静默重解释。
surface hello根节点和 surface identity。文档只允许一个根；根的 key 进入 IR 与诊断。
column / w / h根采用纵向布局并给出逻辑尺寸。逻辑单位不是屏幕物理像素。
text / button子节点用两个空格缩进。按钮没有回调，只有声明过的 semantic intent。

第一轮验证

AI、编辑器或脚本应复用生产 parser/compiler，不要在客户端复制第二套 grammar。

cargo run -p neon-ui-runtime --bin neon3_authoring_probe

探针从 stdin 读取 JSONL，每行输出一个 JSONL 结果；成功结果包含 input schema、canonical IR、节点 outline、预算和 layout hash，失败结果包含 parser/compiler stage 与 source diagnostics。

{"request_id":"hello-1","operation":"validate","sequence":1,"source":"version 1\nsurface hello\n  text title value \"Hello\""}
推荐的工程起点 先用静态 literal text 和一个 button 验证 parse/compile，再增加 input binding；最后才加入 branch、DataGrid、资源和跨进程 host。每加一层都能单独定位失败阶段。
02 / Principles

它为什么这样设计

NUI Flow 的限制不是为了让作者难受，而是为了让 UI 能被编译、检查、重启恢复、跨语言消费，并且不把业务真相偷偷藏进渲染进程。

AUTHORFlow source

人类、AI、Rust、Node 或 Python 都可以生成同一种声明。

UI RUNTIMEParse / lower / validate

产生 UiIrDocument、UiProgram 和 typed diagnostics。

DOMAINFacts / mutations

提供输入帧、文本句柄、网格窗口，接受语义请求。

WGPULayout / hit / pixels

唯一窗口与 GPU owner，负责最终合成和本地反馈。

FEEDBACKSnapshot / intent

领域状态以新 snapshot 回到 UI，UI 不猜测完成结果。

四个 owner，四种责任

NUI FLOW声明

层级、布局、绑定、有限分支、模板能力和 semantic intent。

UI RUNTIME解释

解析、类型验证、编译、输入快照、文本句柄、host adapter 和诊断。

DOMAIN / HOST决定

项目状态、权限、排序、过滤、事务、业务规则和 accepted/rejected。

WGPU RUNTIME呈现

窗口、GPU 资源、布局测量、命中测试、pointer capture、像素和合成。

一条完整的数据回路

domain snapshot
  -> typed input frame { health: f32, title: text_handle }
  -> neon-ui-runtime validates revision + handles
  -> UiProgram evaluates bindings and bounded branches
  -> neon-wgpu-runtime lays out and draws pixels
  -> user activates `terrain.tool.select`
  -> semantic intent crosses the boundary
  -> domain validates, mutates, and publishes a new snapshot
AFlow 不是脚本

没有 callback、循环、网络、文件读取、表达式 evaluator 或任意代码执行。有限 statechart 只负责 UI-local presentation。

BUI 不直接写项目

按钮只产生 intent。项目写入必须经过领域服务和 projectd 的 revisioned 事务。

C画面不等于业务真相

截图可以辅助 visual acceptance，但不能证明 mutation 成功。必须读取 response、snapshot、job 或 trace。

D局部实时反馈留在 WGPU

hover、pressed、滚轮、拖拽预览和 pointer capture 不需要每帧 RPC；语义 begin/end/commit 才走可靠边界。

不能从 UI key 推导业务 identity 640060 一类 renderer hit ID、pointer 坐标、纹理 slot、GPU handle 和数组下标都不能进入 Flow、patch、公共 intent 或项目协议。可见的节点 key 只用于稳定语义定位。
03 / Grammar

语法骨架：逐行、两格、关闭词汇

V1 追求确定性。解析器可以在单行和单个 source span 内给出可重复错误；布局和资源不会因为隐藏的脚本副作用而改变。

词法规则

规则正确写法会发生什么
源编码UTF-8；一行一个 declaration不可识别的行通常会落到稳定 parser diagnostic。
缩进每层正好两个空格Tab 或奇数缩进返回 nui_flow_tabs_forbidden / nui_flow_mixed_indentation。
注释第一处非空字符为 #只支持整行注释；V1 不支持 inline comment。
字符串"hello \"NUI\"\n"支持 \"、\\、\n；空格文本必须整体加引号。
keyterrain.tool-rail_1仅 ASCII 字母、数字、.、_、-；key 是稳定语义名。
拒绝项不写 URL、路径、回调、代码块、任意 JSON、GPU handle返回 ui_program_forbidden_flow_feature，不会 silent no-op。

顶层声明顺序

解析器对部分声明顺序有兼容性，但推荐按下面的顺序维护文件：公共头部 → 输入/资源 → statechart/交互声明 → 唯一根树。

version 1
surface surface.editor.terrain revision 12
flow terrain-workbench
budget nodes=128 bindings=96 instances=128 text=96 glyphs=2048 events=64 clips=32

input can_commit bool default false
input terrain_name text default text:empty
input selected_tool enum:select|sculpt|water default select
resource terrain-preview render_surface

machine terrain initial loading
state terrain ready
sync terrain when $selected_tool=water -> ready

surface workbench row gap 8
  panel inspector column
    text title value $terrain_name
  render terrain-preview

Budget 是编译契约

nodes、bindings、instances、text、glyphs、events、clips 是有界资源上限。编译器会把实际节点、literal text、模板实例和 clip 数量与预算比较。

表面尺寸使用逻辑单位

Flow 不表达物理屏幕像素、DPI、camera matrix 或 GPU viewport。renderer 负责把逻辑布局映射到当前 composition target。

兼容提示：旧 fixture 可能省略 version、revision 或 flow，当前 parser 有默认值/兼容路径；新文件仍建议显式写出版本与 revision，方便诊断和回放。

04 / Inputs

输入与绑定：唯一的数据入口

Flow 不直接访问领域对象。声明一个 input slot，给它类型和默认值，再把这个 slot 绑定到有限的节点属性。文本和资源也遵循同一条边界。

类型清单

Flow 类型示例含义 / 约束状态

i32 / u32 / f32input count i32 default 4数值绑定；可用 i32:min..max 等声明 inclusive range。稳定
enum:a|binput mode enum:alpha|beta default beta变体必须是稳定 key；可用于 combo、tabs、list_box、state 和 enum branch。稳定

Struct、Array 与受限派生值

Struct

input player struct {
  name text
  health f32
  enabled bool default true
}
surface player-card column
  text name value $player.name
  progress_bar hp numeric $player.health
  panel badge visible $player.enabled

当前 schema 会递归计算 packing；parser 可以解析点路径和字段默认值。生产接入请用 authoring probe 验证 compiler 与 host publication 是否支持你的字段路径。

Array + derived bool

input cells array[36] f32
input cell_0_on bool = $cells[0] > 0.5
input cell_1_on bool = $cells[1] > 0.5
surface grid
  panel cell-0 visible $cell_0_on
  panel cell-1 visible $cell_1_on

派生语法只允许一个简单比较：==、!=、>、<、>=、<=。它不是通用表达式语言。

当前实现边界：不要把“parser 接受”当成“全链路稳定” Struct/Array 的类型、packing 和解析测试已经存在，但部分 compiler/evaluator 绑定路径仍按 top-level input key 查找；派生值也需要通过带 schema 的 input replacement path 才会重算。对这两类能力，先执行 neon3_authoring_probe，再接入真实 host。

变量变化观察事件：emitevent

flow terrain-workbench
input brush_size i32:0..24 default 4 emitevent

变化会被命名为 flow.terrain-workbench.brush_size，payload 是结构化 observation，包含 module、surface、variable_key、kind、old/new 值。它不是 domain command；只有明确声明 emitevent 的 slot 才发布，grid 不能使用它。

05 / Layout

布局与样式：逻辑矩形上的确定性规则

Flow 的布局属性进入 canonical IR；WGPU 在实际 viewport 中完成测量、裁剪和最终绘制。不要把逻辑布局和物理像素、命中 ID 混在一起。

    text item-b h 24 value "B"

为什么“标准控件行为”和“皮肤”必须分开？

控件的类型、focus、pressed、pointer capture、keyboard 与 semantic event 是行为契约；skin 只提供有限的 body、track、fill、thumb 等视觉 slot。替换 image 或 nine-slice 不应改变 hit region，也不应让外部拿到 atlas UV。

当前实现已经有 UiControlSkin schema、资源校验、fallback 和多套 fixture；Flow 侧的 skin slot grammar 仍是受限子集，设计稿中更丰富的 token、icon、padding 和固定尺寸不能直接当成稳定语法。

07 / Presentation State

分支、状态机与 motion

NUI Flow 可以声明有限的 UI-local presentation statechart。它能选择预编译 subtree、为样式过渡提供 from/to 快照，并发出一个已声明的 semantic intent；它不能代替领域状态机。

一个可验证的状态机

input workspace_state enum:loading|ready|error default loading
input can_publish bool default false

machine asset_review initial loading
state asset_review ready
state asset_review publishing
state asset_review error

sync asset_review when $workspace_state=ready -> ready
sync asset_review when $workspace_state=error -> error
on asset_review asset.review.publish when $can_publish -> publishing emit asset.review.publish
on asset_review asset.review.retry -> loading emit asset.review.retry

surface review column
  branch loading-view when $workspace_state=loading
    text loading-label value "Loading"
  branch ready-view in asset_review.ready
    text ready-label value "Ready"
  branch publish-view in asset_review.publishing
    text publish-label value "Publishing"
声明输入限制
machine key initial state创建唯一 chartinitial state 必须被声明；state 集合是有限的。
state machine state增加合法目标不创建节点，不访问服务，不改 domain truth。
sync ... when predicatebool 或 enum equality只接受 $flag、!$flag、$mode=ready。
on ... intent已声明 dotted intent先经过 normal semantic-event gate，不能绕过事件验证。
emit intent最多一个 dotted intent只是向 domain 发请求；domain completion 仍通过新 input snapshot 返回。
branch ... in machine.statemachine-local state只隐藏/显示预编译 subtree，不能动态改 topology。

Motion 是显式的 presentation policy

motion panel-expand duration 240 easing ease_out
machine inspector initial compact
state inspector expanded
on inspector inspector.toggle -> expanded
transition inspector compact -> expanded motion panel-expand
style inspector.compact.inspector-panel x 0 y 0 w 280 h 120 opacity 0.82
style inspector.expanded.inspector-panel x 0 y 0 w 520 h 280 opacity 1

surface inspector-root
  panel inspector-panel column w 280 h 120
    text title value "Inspector"

当前 motion 支持毫秒 duration 和 linear、ease_in、ease_out、ease_in_out；state style 可声明 bounds、fill、line、border_width、corner_radius、opacity。renderer 负责采样和插值。

ProgressBar 不等于健康值 tween progress_bar health numeric $health 只表示绑定当前值。若 health 从 82 变化到 30，要由应用/领域动画系统逐 tick 产生合法 input frame；不要在 Flow 里写 animate、时间、回调或业务目标值。
当前集成注意headless state-machine tests 覆盖同步、分支、drag 和 style transition；部分 host refresh helper 仍会以默认 presentation state 重新求值。把状态机用于真实应用前，应验证提交链路是否持续携带 local presentation state，而不是只看到 parser 成功。
08 / Interaction

交互：本地即时反馈，可靠语义提交

高频 pointer 不应该变成每帧跨进程 request。WGPU 在本地完成 hover、focus、capture、scroll 和 preview；语义动作在确定时机通过公共 contract 发出。

  3. host 发送 workspace.card.reparent，带 current revision 和 idempotency key。
  4. domain 校验权限、target schema、placement 和 template，接受后生成新的 revisioned UI program。
  5. UI 只根据 accepted/rejected snapshot 清理 prediction；renderer 从不直接修改 canonical tree。
三种 boundary policywithin parent 将预览限制在 source parent；within surface 限制在 renderer viewport；within free 不施加边界。这些是 presentation policy，不是业务放置规则。

交互生命周期和 revision

pointer down
  -> local hit-test + pointer capture
  -> interaction.begin { interaction_id, renderer_epoch, expected_revision }
  -> local preview / optional coalesced samples
pointer up | cancel | focus loss | epoch change
  -> reliable interaction.end or interaction.cancel
  -> host/domain returns accepted, rejected, or conflict
  -> final snapshot / composition revision

request_id 串联 command、effect、job 和 trace；expected_revision 防止旧状态覆盖新状态；idempotency_key 让断线重试不会重复写入；service epoch 变化时必须丢弃旧 interaction。

09 / DataGrid

DataGrid：有界窗口，不把一万行变成一万个节点

DataGrid 是控制面 grid input + renderer-local scrolling + domain window request 的组合。Flow 只声明列和容量，行 identity、typed cells、display text 和 list revision 都由 domain 提供。

声明一个虚拟表格

容量怎么选

从 viewport 高度和 row height 开始估算：visible_rows ≈ viewport_height / row_height，再给 2–4 行 overscan。容量越大，refill 越少，但每帧 cell/text/control 工作越多。

例如 300 logical px、28 px row：约 11 行可见，capacity 24 或 32 通常是合理起点。

滚动如何跨边界

WGPU 本地处理 wheel、thumb drag、Shift+wheel 和 middle-button pan。可见范围离开当前 frame 时，发送最新的 WindowRequest；旧请求会被 coalesce，不会把每个 raw wheel 事件都变成 RPC。

row index 不是 identity窗口从 480 移到 481 后，first_row 变了，但事件仍使用 stable_row_key + column key。不要把生成的 renderer path 或数组位置写入领域协议。

11 / Revisioned Patches

Patch：用稳定路径更新 canonical IR

当整个 Flow 重编译过重，或工具需要做小范围结构编辑，可以使用 revisioned patch。Patch 改的是 canonical UI document，应用后必须产生新的 document revision，并重新编译验证。

@ revision 12
~ /workbench/tool_rail/water_tool enabled false
+ /workbench/inspector text help_text
- /workbench/inspector/obsolete_help
> /workbench/tool_rail/water_tool /workbench/inspector
操作格式规则
@@ revision 12必须出现；所有 operation 使用同一个 expected revision。
~~ path property value只支持 enabled、visible、value、w、h。
++ parent component key插入 closed-vocabulary node；key 不能已存在。
-- path不能删除 root；目标必须存在。
>> source destination-parent移动 non-root node；不能 self/root move。
路径key 或 /a/b/c只接受 stable semantic keys；纯数字 segment/数组下标会被拒绝。

Dry-run 的用途

  1. 解析 patch，检查 source spans 和 expected revision。
  2. 在隔离的 document copy 上 apply。
  3. 重新执行 canonical IR validation 和 program compile。
  4. 只返回 diff、impacted nodes、预算和 diagnostics；通过后再替换 active program。
Patch 不是领域 mutation它只修改 UI declaration/program。拖放产生的 reparent proposal 仍须交给 domain 验证，domain 接受后才能构造新 UI revision；renderer 不直接调用 patch。

13 / Debug & Acceptance

如何验证，而不是凭截图猜成功

NUI 的验证分成 contract、service、GPU、composition 和 rendered 五层。页面本身只展示工具入口；真实功能仍要在对应 runtime 和 host 上运行。

推荐验证顺序

# 1. parser / lowering / statechart focused tests
cargo test -p neon-ui-runtime nui_flow::tests::
cargo test -p neon-ui-runtime nui_state_machine::tests::

# 2. schema contract
cargo test -p neon-ui-schema

# 3. machine-readable authoring probe
cargo run -p neon-ui-runtime --bin neon3_authoring_probe

# 4. complete UI runtime library
cargo test -p neon-ui-runtime --lib

# 5. source hygiene
git diff --check

15 / Appendix

写作速查与源码证据

把这一节当作提交前的 checklist。完整语义以代码和测试为准；旧报告中与当前 parser 冲突的内容应以本页的状态标记和最新 fixture 为准。

新写一个 Flow 的顺序

1. 先定 owner哪些是 domain facts，哪些只是 UI-local presentation。
2. 列出 inputs每个外部值给出 kind、默认值和必要的 range。
3. 画静态 topology所有 node key 稳定、唯一、有界，容器尺寸明确。
4. 加 binding只使用兼容属性；复杂条件先由 domain 计算成 bool/enum。
5. 加 semantic intent使用领域词，不把 button 编号、坐标或 renderer ID 带出去。
6. parse → compile → probe先 headless，再接 service，再做 GPU/composition capture。
