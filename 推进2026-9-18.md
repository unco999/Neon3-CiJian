当前确实存在两个编辑器状态源：

A. neon-editor-runtime
   document_id
   revision
   ChangeSet
   source_hash
   committed_revision

B. neon-ui-runtime EditorComponent
   EditorCore
   caret
   selection
   scroll
   edit_fx
   UiCodeEditorPresentation
现在 neon-ide 主要是：

文件读写
  -> build_flow
  -> code_editor value/source
  -> full remount
这会导致：

Agent 直接写磁盘；
NUI code editor 再从文件重新加载；
editor-runtime 可能持有另一份文档；
EditorComponent 还有自己的 EditorCore；
revision、dirty、undo、selection、LSP 状态可能互相不一致；
Agent 的 VisualOperation 虽然有 range，但不一定对应 editor-runtime 当前 revision。
所以现在继续堆 shader，会把视觉效果建立在不稳定的文档状态上。正确顺序应该是：

editor-runtime 成为文档权威
  -> bounded ChangeSet
  -> revision ack
  -> EditorBridge 同步 presentation
  -> reveal caret/selection/scroll
  -> shader/edit FX
  -> visual queue complete
关于 source_file

source_file 不应该作为 Agent 编辑路径的主方案。

它可以保留用于：

初始打开静态文件；
demo；
只读预览；
文件切换时加载源内容。
但不应该负责：

Agent 修改；
审批后的写入；
undo/redo；
revision 校验；
多个 Agent session 的变更；
ChangeSet 和 LSP 同步。
Agent 的文件操作应该改成：

Agent tool
  -> 读取 editor-runtime snapshot
  -> 检查 source_hash / revision
  -> 生成 bounded ChangeSet
  -> 审批
  -> editor.document.change.apply
  -> editor.document.change.commit
  -> editor-runtime 返回新 snapshot
  -> 写入磁盘
  -> EditorBridge 生成 presentation
  -> VisualOperation 播放
更准确地说，文件落盘也不应该早于 ChangeSet 成功应用。当前 write_file 是：

std::fs::write
  -> FileWritten / VisualOperation
应该改成：

read snapshot
  -> diff
  -> ChangeSet
  -> apply
  -> commit
  -> persist
  -> VisualOperation
下一步应该怎么做

我建议按这个顺序推进。

确定唯一文档身份
每个打开文件绑定：

EditorDocumentBinding {
    path: String,
    document_id: String,
    session_id: String,
    epoch: u64,
    revision: u64,
    source_hash: String,
}
建议：

document_id = workspace-relative-path
session_id = neon-ide
epoch = editor-runtime 当前 epoch
EditorBridge 不再自己初始化独立 source
EditorBridge 在 sync_fragments 时获取：

code_editor node path
source_file
document_id
然后通过注入的 document provider 获取 editor-runtime snapshot。

这里不能直接在当前同步 render callback 中阻塞 RPC。应该注入一个接口，例如：

trait EditorDocumentProvider {
    fn snapshot(&mut self, document_id: &str) -> Result<EditorSnapshot, String>;
    fn apply_change(&mut self, change: ChangeSet) -> Result<EditorOperationResult, String>;
}
生产环境可以由 command queue / worker 实现，避免 UI render 线程阻塞。

Agent write_file 先变成 ChangeSet
初期可以继续让 Agent 使用完整 write_file 参数，但宿主接到后：

old snapshot.source
new requested content
  -> line diff
  -> EditOp::Insert/Delete
  -> ChangeSet::new(snapshot.revision, ops)
然后调用：

editor.document.change.apply
不应该直接覆盖文件。

处理 revision conflict
如果返回：

editor_revision_conflict
VisualOperation 必须进入：

stale
不能播放 shader，也不能继续队列。

UI 应显示：

文件在 Agent 修改前已被改变，需要重新计算变更
EditorBridge 从 snapshot 生成 presentation
最终 presentation 的 source 应来自：

editor-runtime snapshot.source
而不是直接来自 source_file 或 Flow literal。

然后：

snapshot.revision
  -> UiCodeEditorPresentation.revision
这样 editor ack 才有真实含义。

Reveal 使用真实 document/node 绑定
目前 editor.visual.reveal 已经存在，但应该从：

path -> surface.ide-shell/editor
进一步绑定到：

document_id -> code_editor node path
Reveal 时验证：

document_id
revision
path
range
然后更新：

caret
selection
scroll
presentation revision
最后再接 VisualOperation queue
最终队列完成条件应该是：

ChangeSet applied
  -> new editor revision
  -> presentation revision matched
  -> reveal ack
  -> renderer frame matched
  -> shader completed
结论

我同意另一个 AI 的建议：

现在应该先完善 Editor 的权威数据链路，不应该继续增强 source_file 方案。

当前 Editor 不是“完全没写完”，它的底层能力其实已经不少：

EditorCore
ChangeSet
revision
source hash
selection
caret
scroll
LSP
edit FX
UiCodeEditorPresentation
Reveal
但缺少最关键的生产链路：

editor-runtime document authority
  -> EditorBridge
  -> presentation
  -> Agent ChangeSet
所以准确判断是：

Editor 核心能力：已经有基础
Editor 产品级集成：还没有完成
Agent 编辑闭环：目前不够可靠
下一步我会把当前实现方向切换为：

EditorRuntimeAuthority Phase 1
优先完成：

document_id 绑定；
snapshot provider；
bounded ChangeSet；
revision conflict；
Agent 写入不再直接覆盖文件；
EditorBridge 从 editor-runtime snapshot 生成 presentation。

## 当前执行进度（Neon3 主推进）

已开始实施 `EditorRuntimeAuthority Phase 1`：

- `UiEditorDocumentBinding` 已进入 `neon-ui-schema`，包含 `document_id`、`session_id`、`epoch`、`revision`、`committed_revision`、`source_hash`、`dirty`。
- `UiCodeEditorPresentation` 已携带 document binding；presentation revision 对已绑定文档使用 authoritative document revision。
- `EditorCommit` 已携带 `neon_editor::ChangeSet` 和 document binding，不再只有完整字符串。
- `EditorDocumentProvider` 已加入 `EditorBridge`，支持非阻塞 `request_snapshot`、缓存 `take_snapshot` 和 `submit_change`。
- `neon3-runtime` 已加入后台 editor-runtime RPC provider；fragment/render callback 只读缓存，RPC 在 worker 中执行。
- `editor.document.change.apply` 使用 `kind=commit`，成功响应回填 snapshot cache。
- provider cache miss 时会先请求 snapshot；document 尚未 open 时，使用初始来源在 worker 中调用 `editor.document.open`，再以返回 snapshot 建立 binding。
- headless/windowed WGPU 均在读取 editor presentation 前触发 provider refresh；只有 document revision >= 1 且 source_hash 非空的 authoritative frame 才作为完成状态。

尚未完成：

- 真实 workspace-relative `document_id` 生成与 projectd binding。
- editor-runtime `document.open` 已由 provider worker 接入；仍需端到端验证。
- revision conflict 的 UI stale 状态和重新计算 ChangeSet。
- provider 的端到端 JSONL acceptance probe。
- `source_file` 仍保留为初始打开/demo/兼容 fallback，不能用于 Agent 写入主路径。
这一步完成后，再继续 shader 和 VisualOperation，视觉效果才会真正对应实际编辑内容。

端到端 probe 已通过：`code_editor_authority.v1` 最终 `pass_result:true`，验证 `neon3-runtime -> ui.flow.submit -> provider worker -> editor.document.open -> snapshot cache -> WGPU presentation`；presentation 与 editor snapshot 配对的 `document_id`、`epoch=1`、`revision=1`、`source_hash` 和 source 一致。
