# Neon3 NUI State Animation Plan

Status: active

Progress: M0 parser/schema contracts and M2 numeric renderer sampling are in
progress-complete form. M1 state-to-fragment lowering and M3 Bevy status wiring
remain before the feature is end-to-end.

Owner boundaries: NUI Flow declares presentation state and motion policy. The
NUI runtime owns statechart evaluation and lowering. The WGPU runtime owns
frame-time sampling and pixels. Bevy/domain owns authoritative gameplay values
such as health and mana.

## 1. Current Baseline

The repository already contains most of the renderer-side transition primitive:

- `UiTransition` supports delay, duration, easing, bounds, colors, border width,
  corner radius, and opacity.
- `neon-wgpu-runtime` stores an active transition per stable node key and
  samples from the current rendered visual to the new target visual.
- `NuiFlowStateMachineRuntime` evaluates finite local presentation states and
  produces state transition results.
- `branch ... in <machine>.<state>` selects a precompiled presentation subtree.

The missing links are:

1. NUI Flow has no motion declaration or state-transition-to-motion binding.
2. Flow lowering creates `UiNode.enter_transition = None` for every node.
3. A statechart transition changes branch selection but does not carry motion
   metadata into the evaluated IR/fragment.
4. `UiControlPresentation::Numeric.value` is not sampled by the existing visual
   transition code, so `progress_bar numeric $health` jumps to its target.
5. The current Bevy status source is generated by
   `main.rs::monster_field_flow()` instead of loading a `.nui` document.
6. Accepted external input revision must be read from
   `result.snapshot.scalar_inputs.input_revision` before a following frame is
   sent.

## 2. Target Model

### 2.1 Two state domains

Authoritative domain inputs remain external and typed:

```text
health
mana
level
```

Presentation state remains UI-local:

```text
idle
hit
healing
```

The statechart can choose presentation branches and motion. It must not write
health, infer business success, or replace the domain response.

### 2.2 Motion declarations

The proposed V1-compatible extension is intentionally small:

```text
motion status-hit duration 140 easing ease_in_out
motion health-change duration 320 easing ease_out
```

Motion contains timing policy only. It does not contain callbacks, expressions,
domain values, or renderer handles.

### 2.3 State transition bindings

The proposed explicit form is:

```text
transition status idle -> hit motion status-hit
transition status hit -> idle motion health-change
```

The explicit `from -> to` form is preferred over implicit enter-only behavior:

- it makes reverse transitions possible;
- it avoids replaying an enter animation when a state is reselected;
- it gives the renderer a stable transition identity for diagnostics;
- it maps directly to `NuiFlowStateTransition`.

An optional wildcard form may be added later, but is not required for the first
implementation.

### 2.4 Numeric presentation

`UiTransitionState` will gain an optional numeric value. The renderer will
interpolate `UiControlPresentation::Numeric.value` while preserving its target
min/max range:

```text
UiControlPresentation::Numeric {
    value: sampled_value,
    min: target_min,
    max: target_max,
}
```

This allows Bevy to submit one authoritative `health: 82 -> 100` update. The
renderer displays the intermediate values without generating additional input
frames or revision traffic.

## 3. Proposed Flow Syntax

```text
flow combined-ui

input health f32:0..100 default 82
input mana f32:0..100 default 64

machine status initial idle
state status hit
state status healing
on status character.status.toggle -> hit
on status character.status.reset -> idle

motion status-hit duration 140 easing ease_in_out
motion health-change duration 320 easing ease_out
transition status idle -> hit motion status-hit
transition status hit -> idle motion health-change

surface combined-ui
  panel status-root column w 320 h 140
    progress_bar health-bar numeric $health
    button status-action value "Toggle status" event character.status.toggle
```

The first parser implementation will support only:

- `motion <key> duration <u32> easing <linear|ease_in|ease_out|ease_in_out>`
- `transition <machine> <from_state> -> <to_state> motion <motion_key>`

No arbitrary property list, expressions, callbacks, or numeric animation
expressions will be added to Flow.

## 4. Data Model Changes

### 4.1 Schema

Add to `neon-ui-schema`:

```rust
pub struct NuiFlowMotion {
    pub key: String,
    pub transition: UiTransition,
}
```

Extend `NuiFlowStateTransition` with:

```rust
pub motion_key: Option<String>,
```

Extend `UiTransitionState` with:

```rust
pub numeric_value: Option<f32>,
```

The serialized form must use `serde(deny_unknown_fields)` and remain explicit.

### 4.2 Parsed document

Extend `NuiFlowDocument` with a bounded motion list:

```rust
pub motions: Vec<NuiFlowMotion>
```

Parser validation must reject:

- duplicate motion keys;
- unknown easing values;
- zero/overflowing durations if the contract disallows them;
- transitions referencing an unknown machine, state, or motion;
- transitions whose source/target state is not declared;
- duplicate transition definitions for the same machine/source/target pair.

### 4.3 State machine runtime

`NuiFlowStateMachineRuntime` should return motion metadata with
`NuiFlowStateTransitionResult`:

```rust
pub motion_key: Option<String>
```

The runtime remains responsible only for selecting the declared motion. It does
not sample time and does not mutate the domain.

## 5. Lowering And Fragment Evaluation

The lowering path must preserve motion declarations and state transition
metadata through the compiled program. When presentation state changes:

1. `NuiFlowStateMachineRuntime` returns the selected motion key.
2. The evaluator receives the previous and next presentation state.
3. Entering nodes receive the selected `UiTransition`.
4. Stable nodes whose visual target changes receive the same transition when the
   state transition explicitly applies to them.
5. Existing renderer reconciliation uses stable node keys and starts from the
   current sampled visual, not the original declaration target.

The first implementation may apply a state transition motion to the changed
branch root and its descendants. A later refinement can add a node selector,
but the selector is intentionally out of the first milestone.

## 6. Renderer Work

### 6.1 Existing style path

Reuse the current `ActiveTransition`, `sample`, and `sample_transition` path.
Do not create a second animation scheduler.

### 6.2 Numeric path

Update `sample_transition` so it samples numeric presentation values. Required
behavior:

- numeric value interpolates with the same easing as style;
- min/max remain target values unless a future contract explicitly animates the
  range;
- a target change while an animation is active starts from the current sampled
  numeric value;
- duration zero resolves immediately;
- the final sample equals the target exactly;
- non-numeric controls are unchanged.

### 6.3 Activity and frame loop

The existing `animation_active` / frame wakeup path remains the owner of redraw
activity. Add numeric transitions to its active-transition detection and retain
the current idle behavior after all transitions expire.

## 7. Current Bevy Status Integration

The status flow should eventually be moved from the Rust string builder into a
real `.nui` source so there is one authoritative declaration. The first status
experiment should use:

```text
machine status initial idle
state status hit
on status character.status.toggle -> hit
motion health-change duration 320 easing ease_out
transition status idle -> hit motion health-change
```

The Bevy handler continues to update the authoritative `health` value once.
The renderer owns interpolation.

Before evaluating animation behavior, the host input loop must maintain this
invariant:

```text
next frame expected_input_revision
    == last accepted result.snapshot.scalar_inputs.input_revision
```

Stale frames must not be used to judge animation behavior.

## 8. Implementation Milestones

### M0: Contracts and fixtures

- Add schema structs and serde tests.
- Add parser syntax and diagnostics tests.
- Add a minimal `state-motion.nui` fixture.
- Add a numeric transition fixture.

Acceptance:

- parse/format/compile round trip preserves motion declarations;
- invalid motion references fail deterministically;
- existing fixtures remain unchanged.

### M1: State transition metadata

- Extend state machine declarations/results with `motion_key`.
- Resolve motion references during document validation.
- Carry the selected motion through presentation evaluation.
- Attach `UiTransition` to changed branch roots.

Acceptance:

- dispatching a state intent changes presentation state and returns the expected
  motion key;
- branch evaluation attaches the expected transition;
- no renderer code is needed to understand Flow syntax.

### M2: Numeric sampling

- Add `numeric_value` to transition state.
- Implement numeric interpolation in WGPU.
- Add midpoint, completion, retargeting, and zero-duration tests.

Acceptance:

- a `progress_bar` target update visibly interpolates without Bevy-generated
  intermediate frames;
- retargeting starts at the current sample;
- animation activity expires after completion.

### M3: Bevy status flow

- Extract `monster_field_flow()` into one source file or one canonical embedded
  source path.
- Add status state/motion declarations.
- Keep semantic intent and authoritative health ownership unchanged.
- Verify accepted revision progression and visual animation together.

Acceptance:

- click produces one semantic intent;
- the corresponding input frame is accepted;
- no repeated stale revision warnings;
- health bar transitions from old to new value;
- reversing the state retargets from the current displayed value.

### M4: Diagnostics and capability gating

- Advertise state animation and numeric animation capabilities explicitly.
- Add debug snapshot fields for active transitions: node key, motion key,
  elapsed, duration, and target.
- Keep logs at transition start/reject/completion only; no per-frame logs.

## 9. Test Matrix

Runtime parser/state tests:

```text
cargo test -p neon-ui-runtime nui_flow::tests::
```

Renderer tests:

```text
cargo test -p neon-wgpu-runtime transition --lib
cargo test -p neon-wgpu-runtime animation --lib
```

Required cases:

- motion parse and format;
- transition reference validation;
- state dispatch returns motion;
- branch receives transition;
- style midpoint and completion;
- numeric midpoint and completion;
- numeric retargeting;
- reverse transition;
- zero-duration transition;
- stale/duplicate responses do not create a second transition;
- active animation expires and renderer becomes idle.

## 10. Risks And Decisions

### Risk: statechart and domain state diverge

Mitigation: statechart remains presentation-only. Domain values still arrive as
typed input snapshots. Do not encode health results in statechart transitions.

### Risk: transition is attached to unstable branch nodes

Mitigation: require stable node keys and apply transitions at the branch root
and descendants using existing reconciliation identity.

### Risk: numeric animation creates revision pressure

Mitigation: interpolate only in renderer. Bevy sends one target value per
authoritative update.

### Decision required before M1

Choose whether state motion applies to:

1. the changed branch root and descendants automatically; or
2. explicitly named node keys.

Recommended initial choice: option 1. It matches the current statechart/branch
model and avoids adding a selector grammar before the renderer path is proven.
