Neon3 WorldUi / ScreenUi 性能优化施工计划
0. 总目标
在不改变 Neon3 协议边界的前提下，完成以下目标：

WorldUi 和 ScreenUi 保持统一 GPU ID 图命中。
ID 图只使用 GPU 实际写入的 numeric ID。
numeric ID 必须和同一帧的 UiHitBinding 映射一致。
WorldUi projection 必须立即跟随最新 camera/anchor frame。
UI presentation animation 不能被 camera/anchor projection 重启。
camera/anchor 不允许形成 FIFO RPC backlog。
pointer click 必须优先于低优先级 world frame。
运行时不打印每帧、每节点、全部 binding、bounds、clip。
只在 pointer、semantic click、transition begin/end 等生命周期边界输出 JSONL。
GPU 使用批量 instance buffer 和单次 draw call，禁止每个 panel 一个 draw call。
必须新增真实可执行的 WorldUi 性能/命中验收 probe。
不得使用：
固定坐标补丁
固定点击区域
CPU bounds 作为最终命中结果
重复点击
sleep 掩盖延迟
固定等待毫秒数猜测 GPU ready
每帧打印日志
1. 当前已知问题
1.1 Camera / anchor RPC 会产生过期 frame
当前 host 在：

D:\bevy-nui-host\src\lib.rs
主要函数：

publish_camera_snapshot()
publish_world_anchor()
它们以前会每个 Update 都向同一个 WGPU RPC FIFO 投递：

wgpu.world.camera.submit_frame
wgpu.world.ui.anchor.submit_batch
相机拖动时会出现：

camera_1
anchor_1
camera_2
anchor_2
camera_3
anchor_3
...
旧请求没有价值，但仍然排队执行，导致：

用户相机已经到新位置
renderer 还在消费旧 camera/anchor
WorldUi 视觉延迟追赶
dropped frame 增加
1.2 WorldUi projection 和 presentation transition 混在一个 UiVisual 中
当前 renderer 使用：

UiVisual
UiTransition
ActiveTransition
WorldUi projection 修改：

bounds.x
bounds.y
clip.x
clip.y
presentation animation 也修改同一份 visual。

结果是 camera 移动时：

WorldUi bounds 改变
renderer 认为 target 改变
transition 被重启
animation start time 被刷新
最终表现为：

拖动相机
WorldUi 不立即跟随
动画内容继续播放
过一段时间才追上新的投影位置
必须把以下两类数据分离：

WorldProjectionState:
    screen_x
    screen_y
    view_distance
    world_depth
    frame_sequence

PresentationState:
    width
    height
    background_color
    border_color
    opacity
    numeric_value
World projection 的 x/y 变化不是 animation。

1.3 unified ID 图和 pointer readback 需要有明确的 frame pairing
当前 ID 机制必须保证：

ID texture frame sequence
UiHitBinding map frame sequence
WorldUi anchor frame sequence
ScreenUi fragment revision
属于同一个 composition frame。

禁止出现：

ID 图来自 frame N
hit_bindings 来自 frame N+1
anchor projection 来自 frame N-1
否则会出现：

命中了数字 ID 52
但 52 映射到了错误 panel
1.4 当前 numeric ID 不是跨进程 ID
numeric ID 只能是 renderer 内部 ID。

正确关系必须是：

R32Uint numeric ID
    -> UnifiedIdFrame.binding_by_id
    -> UiHitBinding
    -> stable node path
    -> semantic intent
numeric ID 不得进入业务协议。

稳定身份必须是：

surface.combined-ui/p11
monster.m11

3. 第二阶段：修正 host latest-value 数据流
文件：

D:\bevy-nui-host\src\lib.rs
3.1 不要只使用 in_flight: bool
当前的 camera_in_flight、anchor_in_flight 还不够。

必须增加：

struct LatestCameraFrame {
    frame: CameraFrame,
    signature: WorldFrameSignature,
    dirty: bool,
    in_flight: bool,
}

struct LatestAnchorBatch {
    batch: WorldUiAnchorBatch,
    signature: WorldFrameSignature,
    dirty: bool,
    in_flight: bool,
}
或者使用资源：

#[derive(Resource, Default)]
struct LatestWorldSubmission {
    camera: Option<PendingCameraSubmission>,
    anchors: Option<PendingAnchorSubmission>,
}
规则：

每次 ECS Update:
    计算当前最新 camera/anchor
    如果 signature 和 last_sent 相同:
        不做任何事
    如果不同:
        覆盖 pending latest
        dirty = true

flush:
    如果没有 in_flight 且 dirty:
        发送 pending latest
        in_flight = true
        dirty = false

收到 response:
    in_flight = false
    如果期间又产生新 pending:
        下一次 Update 发送最新值
绝对不能：

收到 response 后无条件清除 last_sent signature
否则静止状态会被重复发送。

3.2 signature 必须避免碰撞
不要只用 DefaultHasher 作为最终正确性依据。

推荐：

#[derive(Clone, Copy, PartialEq, Eq)]
struct WorldFrameSignature {
    camera_position: [u32; 3],
    camera_orientation: [u32; 4],
    fov: u32,
    near: u32,
    far: u32,
    anchor_count: u32,
    anchor_hash: u64,
}
浮点使用：

value.to_bits()
anchor 顺序先按 stable anchor_id 排序，再计算 hash。

hash 只用于性能跳过，真正提交时仍使用完整 typed protocol payload。

3.3 Camera 和 anchor 必须有共同 frame sequence
当前协议类型仍然使用：

CameraFrame
WorldUiAnchorBatch
不要发明新的 JSON transport。

要求：

camera.sequence = world_frame_sequence
anchor_batch.sequence = world_frame_sequence
如果协议要求 camera 和 anchor 各自独立序号，则至少新增内部字段：

{
  "world_frame_sequence": 100
}
不能破坏现有 schema 时，可以在 host 内部维护：

world_frame_sequence
camera_sequence
anchor_sequence
并在诊断 trace 里关联：

{
  "world_frame_sequence": 100,
  "camera_sequence": 100,
  "anchor_sequence": 100
}
3.4 Pointer 不得被 camera/anchor FIFO 阻塞
当前 endpoint worker 按 endpoint 串行。

需要分成至少两条 RPC lane：

world_latest_lane:
    camera frame
    anchor batch

interaction_lane:
    pointer event
    semantic interaction
两条 lane 都使用已有：

length-prefixed JSON over loopback TCP
RpcRequest
RpcResponse
不是发明新协议。

要求：

pointer lane 永远不能等待 world_latest_lane 里的旧请求
可以用两个独立 RpcClient 连接到同一个 WGPU endpoint。

4. 第三阶段：建立持久 unified ID frame
文件：

D:\Neon3\crates\neon-wgpu-runtime\src\lib.rs
D:\Neon3\crates\neon-wgpu-runtime\src\ui_renderer.rs
4.1 不要在 pointer down 时重新绘制整张 ID 图
当前 pointer down 会调用：

read_pointer_hit_id()
该函数会：

创建 command encoder
clear R32Uint
draw_hit_id
copy one pixel
map readback
如果每次 click 都重新完整绘制 ID 图，会产生：

GPU command 重复
CPU/GPU lock 等待
pointer latency 增加
camera drag 时 ID 图反复重建
必须改成：

render loop 负责生成 unified ID frame
pointer down 只读取已完成 ID frame 的一个 pixel
4.2 增加 UnifiedIdFrame
建议：

struct UnifiedIdFrame {
    frame_sequence: u64,
    producer_epoch: u64,
    fragment_revision: Revision,
    world_frame_sequence: u64,
    texture: wgpu::Texture,
    texture_view: wgpu::TextureView,
    binding_by_id: HashMap<u32, UiHitBinding>,
    id_by_node_path: HashMap<String, u32>,
    ready: bool,
}
至少使用双缓冲，推荐三缓冲：

ID ring slot 0
ID ring slot 1
ID ring slot 2
每个 slot 包含：

R32Uint texture
texture view
frame sequence
binding map
fence/readiness state
4.3 ID frame 的生成规则
每个 unified ID frame 必须一次性完成：

1. 获取 combined fragment snapshot
2. 应用 WorldUi anchor projection
3. flatten ScreenUi + WorldUi
4. refresh plan
5. refresh hit bindings
6. 分配 numeric IDs
7. 上传 UiHitInstance array
8. 单次 ID draw call
9. 保存 binding_by_id
10. 保存 frame sequence
11. 提交 GPU
ID 图的 numeric ID 和 map 必须从同一次 refresh_hit_bindings() 生成。

绝对不能：

本帧重新生成 numeric ID
但 pointer 继续使用上一帧 binding map
4.4 Pointer readback 只读取已完成 frame
pointer down 时：

找到最新 completed UnifiedIdFrame
检查 surface/generation/world_frame_sequence
copy 一个像素
read R32Uint
使用同一 UnifiedIdFrame.binding_by_id 映射
如果没有对应 ready frame：

{
  "event": "pointer_id_frame_unavailable",
  "result": "retry_next_frame",
  "reason": "id_frame_not_ready"
}
不要：

重新 draw 一整张 ID 图
sleep
固定等待 16ms
CPU bounds fallback
5. 第四阶段：保证正确的 ID 覆盖顺序

7. 第六阶段：GPU 批处理优化
7.1 ID pass 必须是一个批次
draw_hit_id() 要保证：

所有 UiHitInstance 一次写入 hit_buffer
一次 queue.write_buffer
一次 pass.set_vertex_buffer
一次 pass.draw(0..6, 0..instance_count)
禁止：

for each panel:
    begin render pass
    draw
7.2 预分配 instance buffer
已知 budget：

nodes=512
bindings=512
初始化时直接分配容量：

UiHitInstance capacity = 512
UiInstance capacity = 512
Text capacity = budget
只有超过 budget 才扩容。

不要每帧：

Vec::new()
next_power_of_two()
create_buffer()
推荐：

instances.clear();
instances.extend(...);
queue.write_buffer(...)
保留 capacity。

7.3 静态文本缓存
怪物以下内容是静态：

name
level
title
不要因为：

camera moved
health changed
anchor moved
重新做完整 text layout。

增加：

StaticTextCache {
    fragment_revision,
    node_text_hash,
    glyph_instances,
    atlas_generation,
}
只有以下情况重新布局：

fragment revision changed
font generation changed
text content changed
viewport scale changed
7.4 WorldUi projection 只更新 instance 数据
camera/anchor 变化时：


不重新 parse NUI
不重新 compile program
不重新生成 text glyphs
不重建静态 node topology
只更新:
    root x/y
    width/height scale
    depth
如果当前 renderer 架构无法做到，至少缓存：


flattened topology
node path -> instance index
然后只修改 dynamic fields。

2 = service startup failure

12. 性能验收阈值
在 RTX 3060 Ti、1280x720、50 个 WorldUi panel 下：

steady render avg <= 1.0ms
steady render p95 <= 2.0ms
steady render p99 <= 4.0ms
dropped frames = 0 during idle
dropped frames = 0 during camera drag target load
camera/anchor stale backlog <= 1
pointer down -> ID result p95 <= 5ms
ID result -> semantic event p95 <= 2ms
semantic event -> transition begin p95 <= 5ms
projection update must not restart presentation transition
如果达不到阈值，必须报告：

CPU snapshot time
GPU ID pass time
GPU color pass time
GPU depth pass time
lock wait
RPC queue depth
latest-value overwrite count
dropped count
不能只报告平均 FPS。

14. 推荐施工顺序

Phase 6:

不要用日志数量代替性能指标。
不要用固定延迟掩盖 RPC/GPU 同步问题。
