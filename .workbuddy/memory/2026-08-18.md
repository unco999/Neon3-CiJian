# 2026-08-18

## neon-eventd 事件模块协议设计

- 用户决定新增独立事件中转模块 `neon-eventd`（此前我建议收敛到 sessiond，用户明确
  要求提纯为独立模块），统一中转、走专用事件协议，含高速接口。
- 产出：`plan/neon3-eventd.md`，定义 `neon3.event` 专用协议（EventEnvelope、
  publish/subscribe/ack、schema registry、epoch+全局单调 sequence、幂等、
  环形缓冲重放、断线重连补齐），以及共享内存 SPSC ring fast path（对齐 AGENTS.md
  26.3 契约）与降级策略。
- 核心边界（沿用 AGENTS.md）：变量变动事件是观测通知，不是业务命令；事件 payload
  不携带 GPU handle / element ID / 文件路径；接收方不得把事件当权威状态。
- 未决决策（见文档第 12 节）：环形缓冲默认容量、service.subscribe 保留与否、
  订阅端 ring 首版不做、严格模式默认是否开启。

### 已确认决策（当日补充）

- 严格模式默认开启，未注册事件名直接拒绝。
- 环形缓冲默认 4096 条，可用 `event.retention.get/set` 调整。
- 保留旧 RPC polling `service.subscribe`，平稳迁移。
- 订阅端 ring 首版不做，统一由 eventd fan-out 后走 TCP。

### neon-eventd 实施完成（当日补充）

按 plan/neon3-eventd.md 第 11 节完成全部 5 项：

1. `neon-protocol`：新增 `neon3.event` 专用协议类型（`EventFrame`/`EventResponse` tagged enum、
   `EventEnvelope`/`EventPublish`/`EventSubscribe`/`EventAck`/`EventFilter`/`EventSnapshot`/
   `EventRetention`/`EventError`），publish/subscribe 均带 request_id。
2. `neon-ipc`：公开泛型 `read_json_frame`/`write_json_frame`，`RpcServer::accept()` 支持长连接
   推送，新增 `EventClient`（publish/subscribe 流）。
3. 新建 `neon-eventd` crate：事件注册表（严格模式，预注册 9 个保留命名空间）、全局单调
   sequence、订阅表（filter OR 语义）、4096 条环形缓冲、幂等去重、RPC 控制面
   （service.*/event.snapshot/schema/retention/stats/fastpath.status）、事件服务端按帧
   `protocol` 字段分发 RPC/Event，writer 线程统一写帧。11 个单元测试 + loopback 集成测试。
4. `neon-ui-runtime`：`UiInputApplyResult` 增加 `variable_changes`（含 kind/old/new），
   新增 `event_publisher.rs` 的 `UiVariableEventPublisher`（best-effort 发布
   `nui.variable.changed`），`DemoInputDomain` 加 `with_publisher` 接入。
5. `neon-cli`：新增 `neon event snapshot/subscribe` 命令，`EventCommand` 解析与执行，
   阻塞收 8 条事件后输出。端到端 Python 验证 publish→订阅广播成功。

遇到的坑：
- BufWriter 写帧后必须 flush，否则客户端收不到。
- 订阅 forwarder 线程持有 write_tx clone，Unsubscribe 后需先移除 subscriber 再 join writer
  线程，否则死锁。
- `handle_connection` 必须先读 Value 按 protocol 分发，否则 RPC 帧被当 EventFrame 解析失败。
- Windows target 目录 .cargo-build-lock 偶发"拒绝访问"，删除锁文件或等释放即可。

### eventd 接入 UI Runtime 统一能力（当日补充，架构校正）

用户明确：eventd 不是"大全案例"单独接，而是 **UI Runtime 的基础能力**——所有 Flow 的
`emitevent` 都由 UI Runtime 统一发布，案例只提供声明与 endpoint。接入点落在
`UiHostAdapter`（UI Runtime 内真正 apply input 变化、产生 `variable_changes` 的权威缓存点），
而非 demo domain / neon-dev case。

改动：
- `host_adapter.rs`：`UiHostAdapter` 增加 `publisher` 字段；新增
  `with_event_publisher(eventd_endpoint, client)` builder（从 schema 提取 flow_name/
  emit_event_keys，module=flow_name，surface=schema_id）；`apply_publication` 在
  `scalar.variable_changes` 后 best-effort 发布（不 rollback 已应用帧）。
- `lib.rs`：`UiRuntime` 增加 `eventd_endpoint` 字段 + `with_eventd_endpoint()`；
  `serve_forwarder` 增加 `eventd_endpoint` 参数；`ensure_host_adapter` 激活时
  `.with_event_publisher(self.eventd_endpoint, self.client.clone())`。
- `main.rs`（neon-ui-runtime）：`--forward-server ... [--eventd <ep>]` 解析可选参数。
- `neon-dev`：`ManifestService` 加 `Eventd`（数组 [3]→[4]）；`run_case_session` 无条件启动
  `neon-eventd`（作为 UI Runtime baseline 依赖，不是 per-case fixture），写 session manifest，
  并把 endpoint 以 `--eventd` 传给 ui-runtime forwarder。

关键 bug 修复（真实死锁）：
- `neon-eventd` 的 `handle_rpc` 持有 `core` 锁时调用 `service_description()`→`self.epoch()`，
  而 `epoch()` 内部再次 `self.core.lock()` → **锁内重入死锁**。表现：真实进程
  `service.describe`/`debug.snapshot.get` 超时（`service.health` 用 guard.epoch 直读所以没事），
  neon-dev 的 `query_process_epoch` 卡住 → eventd state 永远 "starting"。修复：`Eventd` 增加
  不可变 `epoch` 字段，`epoch()` 直接返回；`handle_rpc` 的 `debug.snapshot.get` 改为用
  `guard` 直接构造 `DebugSnapshot`（不再调 `self.debug_snapshot()` 重入锁）。

端到端验证（headless 完整链路，Python 驱动）：
- eventd + projectd + wgpu headless + demo_domain_controller + ui-runtime(--eventd)，
  提交 fragment 后发 `ui.host.inbound`（SemanticIntent 切换 feature_enabled），订阅 eventd
  成功收到 `flow.component-gallery.feature_enabled`，sequence=1、epoch=1，payload 含
  module/surface/variable_key/kind/old_value(new_value=true→false)。链路真实打通。

  验证 frame 内容精确匹配）通过；全量 ui-runtime 90 / eventd 11 / neon-dev 2 通过。
