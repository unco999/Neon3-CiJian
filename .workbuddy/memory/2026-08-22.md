## IPC 替换施工（续：服务端并发化切换，14:06 后）

在 neon-ipc 层加了同步桥接（tokio 完全封装在 neon-ipc 内部，调用方无需加 tokio 依赖）：
- `AsyncRpcServer::bind_blocking / bind_blocking_with / serve_blocking / serve_until_blocking`（serve_until_blocking 等价旧 `serve_until` 的 shutdown 语义，用 stop 谓词）。
- `serve_until`（async）加 stop 谓词参数，`handle_connection` 加 stop flag + should_stop；`TransportError::Cancelled` 已加。
- `BlockingRpcClient`：同步 `call`（签名同旧 `RpcClient::call`），内部持 runtime + 持久连接。

已切换的服务端（消除单线阻塞 P0）：
- `neon-wgpu-runtime` `--headless-server`（main.rs）→ `serve_until_blocking` + `Arc<Mutex<WgpuRuntime>>`。
- `neon-wgpu-runtime` `spawn_headless_external_server` → `serve_until_blocking`（handler 原已 Arc<Mutex>，删掉了闭包内 `stop.store` 副作用——serve 返回后函数末尾本就 `stop.store(true)`）。
- `neon-wgpu-runtime` `spawn_window_server` → `serve_until_blocking` + `Arc<Mutex<WgpuRuntime>>`；用 shadow 技巧（`let mut runtime = runtime.lock()` + `let proxy = &handler_proxy`）让 130 行 handler 体几乎不改，靠 `&mut MutexGuard`→`&mut WgpuRuntime` 与 `&&EventLoopProxy`→`&EventLoopProxy` 的 deref coercion。
- `neon-projectd` `serve` → `serve_until_blocking` + `Arc<Mutex<Projectd>>`。

未改（需领域层设计，非 transport 替换）：
- `neon-ui-runtime::serve_forwarder`：串行是领域语义（host forward 顺序 + active_host_forwards 状态机 + deferred queue），需自驱动 dispatcher + job 模型。
- 客户端每请求连接的高频 forward 路径：需连接池（HashMap<SocketAddr, BlockingRpcClient>）。
- `neon-eventd`：已是每连接线程并发，无需改。

关键教训：service handler 的 `&mut` 独占借用可用 `Arc<Mutex<>>` + 闭包开头 shadow MutexGuard 的办法最小化改动；闭包若需 `move`（'static）捕获 Arc，注意不要 move 掉函数后续仍要用的局部 Arc（可 clone 或删掉闭包内冗余副作用）。

## IPC 替换施工（bug 修复：服务端连不上 os error 10061）

症状：bevy-nui-host 连不上，`transport_io: 由于目标计算机积极拒绝，无法连接 (os error 10061)`，`ui_flow_submit_failed`。根因**不是协议问题**（bevy 客户端无需任何改动，wire 格式/JSON 协议未变），而是上一轮 blocking 封装的 bug：

- `AsyncRpcServer::bind_blocking` 用**临时 current_thread runtime** 做 bind，listener 注册到该 reactor；`serve_until_blocking` 又用**另一个 multi_thread runtime** 跑 serve。tokio `TcpListener` 的 accept 依赖原 reactor，原 reactor 已 drop → accept 失败 → serve 退出 → 端口释放 → 客户端连接被拒。

修复：删掉 `AsyncRpcServer::{bind_blocking,bind_blocking_with,serve_blocking,serve_until_blocking}`，新增 `BlockingRpcServer`（持 `runtime: Runtime + server: AsyncRpcServer`），`bind` 和 `serve_until` 都 `block_on` 在**同一个** runtime 上（`let Self { runtime, server } = self;` 解构后 `runtime.block_on(server.serve_until(...))`）。调用方改：`AsyncRpcServer::bind_blocking`→`BlockingRpcServer::bind`，`.serve_until_blocking(...)`→`.serve_until(...)`。已同步改 main.rs、wgpu-runtime lib.rs（headless external + window server）、projectd。

核心教训：**tokio 的 listener/connection 必须与其 serve 的 accept/poll 在同一个 runtime 上**（listener 注册到创建它的 reactor）；同步桥接层必须让 bind 和 serve 共享同一个 runtime，不能各自临时建 runtime。

另：日志里的 `Unknown vertex attribute TEXCOORD_2` 是 Bevy 渲染侧（mesh 缺 TEXCOORD_2 顶点属性），与 IPC 无关。
